## Contexto
Repositório estava vazio no início desta entrega (sem CLAUDE.md, sem código, sem git). Stack padrão da V01 adotada integralmente: NestJS + TypeScript estrito + Prisma/PostgreSQL no backend; Next.js + Tailwind/shadcn no frontend (fase 3). Nenhuma base anterior foi reaproveitada ou removida — não havia nada a reaproveitar.

## Ordem obrigatória
1. Backend e banco (em andamento)
2. API
3. Frontend

Não avançar de fase sem o gate da fase anterior fechado.

## Escopo P0 (dentro da V01)
- Multi-tenancy hierárquico: ADM/Super Admin → Revenda → Cliente → Condomínio, com isolamento reforçado em código e no PostgreSQL (RLS).
- Autenticação, sessões, MFA preparada (não obrigatória na V01), RBAC, feature flags.
- Bootstrap seguro do primeiro Super Admin via variável de ambiente protegida, com troca obrigatória de senha no primeiro login.
- White-label por tenant (logo, nome, favicon, cores, domínio) conforme permissão delegada.
- Núcleo condominial: condomínios, blocos/unidades, moradores, dependentes, veículos, prestadores.
- Portaria e acessos: visitantes, entregas (com Portaria Rápida e fluxo de retirada por código/QR), controle de chaves, acesso de veículos/prestadores.
- Segurança operacional: ocorrências, checklist, passagem de plantão, botão de pânico, lista de bloqueio, incidentes.
- Comunicação: comunicados, notificações, adapter/outbox para WhatsApp (sem integração real obrigatória na V01).
- Telefonia residencial: um ramal PJSIP por unidade, fila FIFO por unidade, gravação por política, relatórios de chamadas.
- Auditoria, privacidade/LGPD (consentimentos, solicitações, exportação, retenção/legal hold).
- Relatórios essenciais (acessos, visitantes, entregas, prestadores, ocorrências, chamadas).
- Painel separado do Super Admin (SaaS): revendas, clientes, planos/módulos, provisionamentos, white-label global, suporte assistido, auditoria da plataforma.

## Decisões registradas
- Stack padrão da V01 adotada sem alteração (repositório era vazio, sem ADR de migração necessário).
- Primeira fatia da Fase 1: scaffold NestJS, config/env validation, logging estruturado, health checks, schema Prisma inicial de tenancy.
- Isolamento de tenant em duas camadas: aplicação (escopo derivado só da sessão) + Postgres RLS com `FORCE ROW LEVEL SECURITY`. Descoberto durante os testes que superusuários ignoram RLS mesmo com FORCE — por isso a aplicação conecta com um papel restrito (`portalia_app`, ver `backend/prisma/provisioning/create-app-role.sql`), separado do papel usado só para migrations.
- Refresh tokens são opacos (aleatórios, hash SHA-256 persistido), não JWT — permite revogação real e detecção de reuso (token já rotacionado sendo reapresentado revoga toda a cadeia daquele usuário).
- RBAC da V01 é uma matriz estática papel → permissão (`backend/src/auth/rbac/permissions.ts`), sem tabela de permissões customizadas por usuário. Suficiente para o escopo P0; extensível depois se necessário.
- `feature_flags` não tem RLS (resolução "efetivo" precisa ler vários níveis da hierarquia em uma query, o que uma política por linha não expressa bem); visibilidade de escrita fica na camada de aplicação.
- Bootstrap do Super Admin é idempotente (`npm run bootstrap:super-admin`), lê credenciais de env vars protegidas e força troca de senha no primeiro login.
- Núcleo condominial (Unit/Resident/Vehicle/Provider) e módulos operacionais (Visitor+VisitorAuthorization, Delivery com código de retirada, KeyRecord com check-out/devolução, Occurrence, PanicAlert, BlockListEntry) seguem o mesmo padrão: `resale_id/client_id/condominium_id` denormalizados em cada linha, trigger de consistência contra o ancestral real, RLS de três níveis, e um `CondominialService`/`GatehouseService`/`SecurityService` que checam RBAC e gravam auditoria (sucesso e falha) para cada escrita.
- **Fase 1 (Backend/Banco) fechada**: gate 100% verde.
- **Fase 2 (API) iniciada**: prefixo `/api/v1`, Swagger em `/api/docs`. Access token JWT curto (Bearer, `Authorization` header) + refresh token opaco em cookie HttpOnly `SameSite=Strict` escopado a `/api/v1/auth`. CSRF via double-submit cookie, mas só nos endpoints que autenticam por cookie (`refresh`/`logout`) — o resto usa Bearer, que navegadores não anexam automaticamente, então não é explorável por CSRF. Rate limit global (100 req/min) + limites mais estritos em login (5/min) e refresh (10/min) via `@nestjs/throttler`. Idempotency-Key obrigatório (header) em escritas críticas, com cache de resposta em `idempotency_keys` (sem RLS — é um cache interno por `(key, rota, ator)`, nunca listado). Toda resposta de erro segue um envelope padrão `{error: {code, message, correlationId, details}}`, com `correlationId` = request id do pino, propagado no header `X-Correlation-Id`. DTOs de entrada validados com os mesmos schemas Zod do domínio (via `ZodValidationPipe` escopado por parâmetro — **cuidado**: `@UsePipes` a nível de método valida TODOS os parâmetros do handler, não só `@Body()`; isso causou um bug real nesta sessão onde o pipe tentava validar o objeto `Actor` injetado por `@CurrentActor()` contra o schema do body). Nenhuma entidade Prisma bruta é devolvida — cada recurso tem um mapper de resposta.
- Recursos de portaria/segurança expostos via HTTP: `POST /gatehouse/visitors`, `POST /gatehouse/deliveries` + `POST /gatehouse/deliveries/:id/collect` (Portaria Rápida), `POST /gatehouse/keys` + `check-out`/`return`, `POST /security/occurrences`, `POST /security/panic-alerts` (sem `@RequirePermission` fixo — aceita `GATEHOUSE_OPERATE` OU `SECURITY_OPERATE`, checado no service, não dá pra expressar isso com um guard de permissão única), `POST /security/block-list`.
- Corrigido no filtro global de exceções: erros do Prisma que refletem engano do cliente (P2002 unicidade, P2025 não encontrado) agora viram 409/404 no envelope padrão, em vez de vazar como 500 não tratado — pego durante os testes HTTP reais (documento duplicado na lista de bloqueio).
- Padrão de recurso (controller fino + mapper de resposta + `@Idempotent`) está replicado e validado em 13 endpoints de escrita e 7 de listagem paginada, cobrindo 100% do núcleo condominial + portaria/segurança da Fase 1. O que falta na Fase 2 (administração SaaS, relatórios, white-label etc.) é mecânico de replicar quando chegar a vez, mas ainda não tem caso de uso de domínio por trás — precisa ser modelado primeiro.
- **Novo módulo `tenancy`**: CRUD de Resale/Client/Condominium (o topo da hierarquia, que só existia via seed direto no banco até agora). `resaleId`/`clientId` no corpo da requisição são **sempre ignorados** para atores escopados (RESALE_ADMIN, CLIENT_ADMIN etc.) — o valor efetivo vem só do escopo do ator autenticado, nunca do payload. Só SUPER_ADMIN (sem escopo próprio) precisa informar explicitamente o `resaleId`/`clientId` alvo. Testado via HTTP com um "spoofing attempt" real (corpo tentando criar recurso sob o tenant de outro ator) — o valor do corpo é descartado, não gera erro nem sucesso indevido.
- **Bug de RBAC corrigido nesta rodada**: `CLIENT_ADMIN` não tinha `CLIENT_MANAGE` (permissão para criar condomínios sob o próprio cliente) — inconsistente com a descrição do produto ("Cliente enxerga... seus condomínios"). Corrigido e coberto por teste.
- **Bug de teste corrigido**: `afterAll` de um teste apagava `client`/`condominium` antes de apagar o `user` que os referenciava (violação de FK), o que deixava um usuário `SUPER_ADMIN` órfão no banco entre suites — e isso quebrava silenciosamente o teste de bootstrap idempotente de um arquivo totalmente diferente rodando depois. Mesma classe de bug apareceu de novo no arquivo de teste de usuários (um usuário criado via API dentro do teste não foi adicionado à lista de limpeza). Lição: em `--runInBand` com banco compartilhado entre arquivos de teste, uma falha de cleanup vaza estado para os testes seguintes, não fica isolada no arquivo que falhou — por isso passei a limpar por `resaleId`/tenant, não só por lista de e-mails rastreados manualmente, como rede de segurança.
- **Novo módulo `users`**: provisionamento hierárquico de contas. `ROLE_DEPTH` (`auth/rbac/role-hierarchy.ts`) mapeia cada papel a uma profundidade na árvore (0=plataforma, 1=revenda, 2=cliente, 3=condomínio); um ator só pode provisionar papéis na sua própria profundidade ou mais fundo — nunca acima, e **nunca outro SUPER_ADMIN** (essa conta só existe via `bootstrap:super-admin`, nunca pela API). O tenant efetivo do novo usuário vem do escopo do ator quando o ator já está naquele nível (mesma regra "nunca confiar no payload" do módulo tenancy); quando o ator está acima do nível do papel-alvo (ex.: revenda criando um Condo Manager), o id mais profundo enviado no corpo é validado contra a cadeia real via leitura escopada por RLS antes de aceitar. Testado com uma tentativa real de cross-tenant (revenda A tentando provisionar usuário sob um cliente da revenda B) — bloqueado, e nenhum usuário fica órfão no banco quando isso acontece.
- **Painel Super Admin** — quatro peças novas:
  - `platform/audit-logs`: leitura do trilho de auditoria já gravado desde a Fase 1 (nada de novo a popular, só uma consulta paginada e escopada por `resolveTenantScope`).
  - `platform/feature-flags`: `FeatureFlagsService` já existia (Fase 1) sem endpoint HTTP; adicionei `setFlag`/`listForScope`. **Bug real encontrado e corrigido antes de testar**: `listForScope` inicialmente retornava flags de *todas* as revendas para qualquer ator com `FEATURE_FLAG_MANAGE` — um Resale Admin veria flags de outra revenda. `feature_flags` não tem RLS (decisão da Fase 1: resolver "efetivo" precisa ler vários níveis, o que RLS por linha não expressa), então a restrição por árvore de tenant teve que ser feita na camada de aplicação.
  - `platform/white-label`: novo modelo `WhiteLabelConfig`, mesmo formato de escopo do feature flag (GLOBAL/RESALE/CLIENT/CONDOMINIUM), mas com **merge campo a campo** do mais genérico pro mais específico (um condomínio que só troca a logo ainda herda as cores da revenda), em vez de "linha mais específica vence tudo" como o feature flag.
  - `platform/plans` (+ `/assign`): catálogo de planos (nome + lista de módulos, sem cobrança real) e "provisionamento" = atribuir um plano a uma revenda (`Resale.planId`).
  - Escrita em `feature-flags`/`white-label` compartilha `resolveWritableScopeId` (`auth/rbac/scope-authorization.ts`): só SUPER_ADMIN escreve em GLOBAL; um ator só escreve no seu próprio nível ou mais fundo, e quando escreve mais fundo que o seu nível o id é validado contra a árvore real via leitura escopada por RLS — mesmo desenho usado em `tenancy` e `users`, terceira vez que esse padrão se repete, por isso virou helper compartilhado em vez de copiado de novo.
  - **Lição de teste**: o rate limit de login (5/min, por IP) é real e correto — um arquivo de teste que faz login para 6+ atores diferentes na mesma suíte estoura o limite e quebra em cascata com 401 (não 429, porque o token fica `undefined` e a chamada seguinte falha por falta de token, mascarando a causa raiz). Corrigido reduzindo para 2 logins por arquivo (1 super admin + 1 resale admin, reutilizados entre sub-testes) em vez de logar um ator novo a cada `it()`. Regra que vale para qualquer novo arquivo de teste HTTP daqui pra frente.
- **Novo módulo `reports`**: agregações sobre dados que já existem desde a Fase 1 (nenhuma tabela nova) — `GET /reports/overview` (contagens operacionais correntes de um condomínio: unidades, moradores, veículos, prestadores ativos, visitantes hoje, entregas pendentes, ocorrências abertas, chaves retiradas, alertas de pânico não resolvidos) e `GET /reports/{deliveries,occurrences,visitors,providers}` (contagem por status/severidade, com filtro opcional de período). Relatório adiciona valor por agregação — não duplica as listagens que já existem em `condominial`/`gatehouse`/`security`. Reports de "Acessos" e "Chamadas, filas e gravações" do sidebar da V01 ainda não têm dado de origem (não existe um `AccessLog` genérico para veículos/prestadores, e telefonia depende do Asterisk) — ficam para quando esses módulos existirem.
- **Novo módulo `notifications`**: `Announcement` (comunicado, escopado por condomínio) + `NotificationOutboxEntry` (uma linha por tentativa de envio, canal/destinatário/status/motivo). `POST /notifications/announcements` cria o comunicado e automaticamente faz fan-out para todo morador ativo com telefone cadastrado (um outbox entry por morador). **WhatsApp é só adapter/outbox "pronto para plugar"** — `WhatsAppAdapter` (`notifications/adapters/whatsapp.adapter.ts`) é deliberadamente um stub que sempre falha com um motivo explícito ("adapter não configurado nesta instalação") em vez de fingir sucesso; isso é proposital, não uma pendência esquecida — a regra de segurança do projeto proíbe declarar WhatsApp como homologado sem teste real contra um provedor de verdade, e a V01 não integra nenhum. `GET /notifications/whatsapp/status` expõe esse estado honestamente para a UI (Conexão WhatsApp aparece como desconectada). Trocar por um provedor real no futuro é só implementar `NotificationChannelAdapter.send()` contra a API do provedor e virar `isConfigured()` para `true` — nada no resto do pipeline (fan-out, outbox, auditoria) precisa mudar.
- **Débito registrado, não implementado nesta rodada**: o stack padrão da V01 pede Redis + BullMQ para jobs assíncronos/outbox; o dispatch do outbox aqui é síncrono (tentado na mesma requisição que cria o comunicado), não teria como escalar para milhares de moradores sem bloquear a resposta. Aceitável para V01 (volume baixo, WhatsApp nem está conectado de verdade), mas quando um provedor real entrar, o dispatch deveria migrar para um worker BullMQ processando a fila do outbox de forma assíncrona — ainda não configurado nesta sessão (nem Redis está rodando no ambiente de dev).
- **Novo módulo `privacy`**: `Consent` (consentimento por finalidade — ex.: `call_recording`, `photo_capture`), `DataSubjectRequest` (solicitação LGPD: ACCESS/CORRECTION/DELETION/PORTABILITY, com workflow OPEN→COMPLETED/REJECTED) e `LegalHold` (retenção — bloqueia aprovação de uma solicitação de exclusão enquanto ativo, testado ponta a ponta: cria hold → solicitação de exclusão → aprovação bloqueada com 409 → hold levantado → aprovação passa). **Gap real e documentado, não escondido**: `Resident` não tem campo de documento (CPF) no schema da V01, então a exportação (`GET /privacy/requests/:id/export`) só consegue casar automaticamente Visitor/Provider/BlockListEntry (que têm `document`) contra o documento do titular — moradores ficam de fora do best-effort e a resposta inclui uma nota explícita sobre isso. Corrigir isso exigiria adicionar `document` a `Resident`, uma migration própria — não fiz agora para não misturar com este módulo, mas está registrado como próximo passo natural.
- Igual a `tenancy`/`users`/`platform`: nenhuma escrita neste módulo confia em tenant id do payload — sempre resolve via `resolveTenantScope(actor)` e reconfirma a cadeia (condomínio pertence ao cliente/revenda do ator) via leitura escopada por RLS antes de gravar.
- **Novo módulo `telephony`** (fecha o P0 restante da Fase 2): `Extension` (um ramal por unidade, senha SIP cifrada em repouso, nunca hasheada — precisa ser reversível porque um provisionamento PJSIP real teria que ler a senha de volta; AES-256-GCM via `TELEPHONY_SIP_SECRET_KEY`, formato `iv:authTag:ciphertext`), `Call` (estado da chamada, com timestamps por transição: `queuedAt`/`ringingAt`/`answeredAt`/`endedAt`) e `Recording` (metadados apenas — sem armazenamento real de mídia). **Fila FIFO é uma view derivada, não uma tabela própria**: uma chamada nasce `QUEUED` (em vez de `RINGING`) quando o ramal de destino já está ocupado (`RINGING`/`ANSWERED` em qualquer lado da chamada), e ao encerrar uma chamada ativa a mais antiga `QUEUED` daquele mesmo ramal é promovida — exatamente o exemplo obrigatório do prompt mestre (unidade 8 em chamada com a portaria, unidade 5 liga e espera até 8 desligar, 5 desistir, ou timeout). Cobre também desistência (`ABANDONED`) e timeout (`TIMEOUT`) explícitos via endpoint dedicado (não há um timer real na V01 disparando isso sozinho).
- **Nenhum Asterisk real conectado na V01** — `POST /telephony/events` é o webhook que uma futura ponte AMI/ARI chamaria (`CALL_STARTED`/`CALL_ANSWERED`/`CALL_ENDED`), autenticado por HMAC-SHA256 (`X-Signature`/`X-Timestamp`/`X-Nonce`, tolerância de 5 min, nonce gravado em `webhook_nonces` — sem RLS, propositalmente, é um controle de replay global, não um dado por tenant) em vez de JWT, já que quem chama não é um usuário logado. Processamento é idempotente por natureza (replay do mesmo evento não duplica nem quebra: `CALL_STARTED` repetido retorna a chamada já existente pelo `externalCallId`; `CALL_ANSWERED`/`CALL_ENDED` em uma chamada já nesse estado terminal é no-op). `originateCall` (a única ação que a própria UI dispara direto, sem depender do webhook) exige o mesmo `TELEPHONY_OPERATE` que ramais e fila.
- **Bug de RBAC corrigido nesta rodada**: `CONDO_OPERATOR` não herdava `TELEPHONY_OPERATE` apesar de existir um array `ALL_CONDO_LEVEL` com essa permissão — o array só era espalhado (`...ALL_CONDO_LEVEL`) no `CONDO_MANAGER`, o `CONDO_OPERATOR` tinha um `Set` próprio, escrito à mão, que nunca foi atualizado quando `TELEPHONY_OPERATE` foi adicionado. Sem correção, o operador de portaria — exatamente quem atende o interfone no dia a dia — não conseguiria originar chamada nem operar a fila. Pego pelo teste unitário de permissões, não em produção.
- **Bug real e sério corrigido nesta rodada, fora do escopo de telefonia mas achado através dela**: todo access token JWT emitido pela aplicação (não só telefonia — login, refresh, todo fluxo autenticado) expirava no mesmo segundo em que era emitido (`iat === exp`), tornando qualquer requisição autenticada que não caísse no mesmo milissegundo do login um 401. Causa raiz: `ConfigModule.forRoot({ load: [loadConfig] })` usa o mecanismo `load` do `@nestjs/config`, que popula um bucket interno consultado *depois* de `process.env` bruto em `ConfigService.get()`. Como toda env var validada pelo Zod (`JWT_ACCESS_TTL_SECONDS=900`, coagida para `number` via `z.coerce.number()`) também existe literalmente em `process.env` como string, `config.get('JWT_ACCESS_TTL_SECONDS', {infer:true})` sempre devolvia a string bruta `"900"`, nunca o número coagido — `{infer:true}` só afeta o tipo em compilação, não a ordem de resolução em runtime. `jsonwebtoken` trata `expiresIn: "900"` (sem unidade) como uma duração inválida/zero, não como 900 segundos. Corrigido trocando `load` por `validate: validateEnv` em `ConfigModule` (`backend/src/config/config.module.ts`) — essa é a opção que o `@nestjs/config` documenta especificamente para popular o bucket "validado" que `get()` prioriza antes do `process.env` bruto. `backend/src/config/configuration.ts` (o `loadConfig` antigo) foi removido por ter ficado sem uso. Suíte completa de e2e (14 arquivos, 79 testes) reexecutada do zero após a correção para confirmar que nada dependia do comportamento quebrado por sorte de timing.
- Suíte de testes do módulo: `telephony/sip-credential.crypto.spec.ts` (round-trip de cifra, IV único por chamada, falha com chave errada), `telephony/dto.spec.ts` (validação Zod, incluindo o discriminated union de eventos do webhook) e `test/telephony-http.e2e-spec.ts` (criação de ramal com senha em texto puro devolvida uma única vez, o exemplo obrigatório de fila FIFO ponta a ponta, abandono/timeout, ciclo completo do webhook com idempotência de replay, assinatura HMAC inválida/expirada/nonce reutilizado rejeitados, permissão negada sem `TELEPHONY_OPERATE`). Suíte completa (unitários + e2e) verde após as correções acima.

## Fase 3 — Frontend (iniciada)

- **Scaffold**: Next.js 16 (App Router, Turbopack) + TypeScript estrito + Tailwind v4 + shadcn/ui (primitivas Radix, preset Nova) em `frontend/`. Dependências principais: zustand (estado de sessão), TanStack Query (dados do servidor), react-hook-form + zod (formulários, mesma biblioteca de validação do backend), next-themes (tema claro/escuro).
- **Pré-requisito no backend que não existia**: CORS estava totalmente desabilitado (`main.ts` nunca chamava `enableCors`) — impossível o frontend, em outra origem, mandar cookies. Adicionado `app.enableCors({ origin: FRONTEND_URL, credentials: true, ... })` com uma nova env var `FRONTEND_URL` (default `http://localhost:3000`, obrigatoriamente uma origem exata, nunca wildcard, porque a sessão depende de cookies).
- **Fluxo de autenticação**: access token JWT vive só em memória (Zustand), nunca em `localStorage`/`sessionStorage` — perde-se num reload forçado por desenho (mitiga XSS). Ao montar, a store tenta uma `POST /auth/refresh` silenciosa usando o refresh cookie httpOnly; o CSRF token (obrigatório nesse endpoint via double-submit) é persistido em `sessionStorage` no login/refresh anterior porque `document.cookie` **não** consegue ler o cookie CSRF do frontend — o cookie tem `Path=/api/v1/auth`, e path de cookie restringe leitura via JS pelo path do *documento atual*, não só pelo host; nenhuma página do frontend nunca está sob esse path, então o cookie nunca aparece em `document.cookie` em nenhuma página, mesmo em dev com front/back no mesmo host.
- **Bug sério de sessão corrigido nesta rodada**: dois `refresh()` concorrentes (Strict Mode do React em dev invoca efeitos duas vezes; ou uma corrida entre `init()` e o retry-após-401 do cliente HTTP) apresentavam o **mesmo** refresh token ao backend. O backend rotaciona o token a cada `/auth/refresh` bem-sucedido e trata reapresentação de um token já rotacionado como roubo — revogando **toda** a cadeia de sessão daquele usuário (`RefreshTokensUseCase.revokeAllActive`). Ou seja: a corrida no frontend derrubava a sessão do próprio usuário no ato de tentar restaurá-la. Corrigido compartilhando uma única Promise em voo entre todos os chamadores de `refresh()` (`inFlightRefresh` em `session-store.ts`) — qualquer chamador concorrente recebe o mesmo resultado em vez de disparar uma segunda requisição.
- **Bug corrigido**: `POST /auth/logout` exige `JwtAuthGuard` (Bearer) *e* `CsrfGuard`, mas o cliente só mandava o header CSRF — todo logout retornava 401 e a sessão nunca era revogada no servidor (o refresh token continuava válido até expirar sozinho, 30 dias). O estado local era limpo mesmo assim, dando a falsa impressão de logout. Corrigido enviando `Authorization: Bearer` também nessa chamada.
- **Bug real corrigido no backend, achado por acidente aqui**: `POST /auth/refresh` sem o cookie de refresh presente devolvia HTTP 200 com um corpo `{error:{...}}` em vez de um 401 de verdade (código defensivo antigo que nunca tinha sido exercitado por um teste HTTP real). Corrigido para `throw new UnauthorizedException(...)`, consistente com o resto da API.
- **Bug de UI sério corrigido**: `Dialog`, `Sheet`, `Select`, `DropdownMenu` e `Tooltip` gerados pelo `shadcn` usam classes de animação de saída (`data-closed:animate-out ...`, convenção do plugin `tw-animate-css`) que, nesta combinação exata de versões (Next 16/Turbopack, Tailwind v4, React 19.2, `radix-ui` 1.6, `tw-animate-css` 1.4), nunca disparam `animationend` — o elemento overlay fica com `data-state="closed"` mas continua em `display:grid`/`pointer-events:auto` para sempre, bloqueando cliques em **todo o app** depois do primeiro diálogo fechado. Corrigido removendo as classes de animação de saída desses cinco componentes e trocando por `data-closed:hidden` (oculta instantaneamente via CSS, sem depender do Presence do Radix aguardar uma animação que nunca termina). Verificado via DOM real no browser (não só leitura de código) antes e depois da correção.
- **Módulo `platform/tenancy` (frontend)**: uma única página com drill-down (Revendas → Clientes → Condomínios) em vez de três rotas separadas, porque a API já modela a hierarquia assim (list exige o id do nível pai) e a maioria dos papéis só enxerga um nível fixo (`RESALE_ADMIN` nunca vê a lista de revendas, por exemplo — a página entra direto no nível do escopo do ator, usando `ROLE_DEPTH` para decidir o ponto de entrada). Criação em cada nível é individualmente gated pela mesma permissão que o backend exige (`PLATFORM_MANAGE`/`RESALE_MANAGE`/`CLIENT_MANAGE`).
- **Módulo `users` (frontend)**: formulário de criação com seletor de papel filtrado por `canProvisionRole` (mesma regra de `ROLE_DEPTH` do backend) e pickers de revenda/cliente/condomínio que aparecem só quando o escopo do ator não fixa aquele nível — espelha exatamente `UsersService.resolveEffectiveScope` no backend.
- **Decisão de escopo desta fatia**: só as duas telas acima foram construídas (mais login, troca de senha obrigatória, e um `/inicio` honesto para papéis sem módulo operacional ainda). Gatehouse, segurança, telefonia, relatórios, notificações, privacidade, white-label e o painel completo do Super Admin ficam para as próximas rodadas — cada nova tela só entra no menu (`nav-config.ts`) no mesmo commit em que a página fica funcional, nunca antes.

## Entregas com evidência fotográfica, credencial de retirada e WhatsApp

Rodada guiada pelo sistema de referência **PortariaFlow v11.56** (fornecido como zip), replicando layout e funcionalidades de entregas/retiradas e personalização.

- **Endpoints de listagem que faltavam**: gatehouse e segurança só tinham `POST`. Uma tela de portaria precisa ver a fila de entregas pendentes e as chaves retiradas para agir sobre elas, então entraram `GET` paginados para visitantes, entregas, chaves, ocorrências, alertas de pânico e lista de bloqueio. Todos gated por `GATEHOUSE_OPERATE`/`SECURITY_OPERATE` (não `REPORTS_VIEW`): o `CONDO_OPERATOR` não tem `REPORTS_VIEW` e precisa enxergar a própria fila.
- **Bug de permissão corrigido**: `GET /condominial/units` exigia `REPORTS_VIEW`, o que impedia o porteiro de escolher a unidade em qualquer ação (entrega, visitante, chave, chamada). A checagem virou um OU no `CondominialService.assertCanListUnits` — listar unidades é pré-requisito de praticamente toda escrita de nível condomínio.
- **Fotos operacionais** (`OperationalPhoto` + `StorageService`): os bytes ficam fora do Postgres (disco local na V01, com interface de object store para trocar por MinIO/S3 sem tocar em quem consome); no banco ficam chave do objeto, metadados, e a linha entra no mesmo escopo de RLS/auditoria do resto. **O tipo da imagem é verificado pelos bytes reais (magic numbers), não pelo `content-type` declarado** — um `.png` com conteúdo de texto é rejeitado (verificado por requisição real). A `objectKey` é resolvida contra o diretório raiz para impedir path traversal.
- **Entrega com foto nos dois atos**: `receiptPhotoId` no recebimento e `pickupPhotoId` na retirada, ambos com trigger no banco garantindo que a foto pertence ao mesmo condomínio da entrega.
- **Credencial de retirada com dois portadores**: um código numérico de 6 dígitos (que o morador recebe no WhatsApp e dita na portaria) e um token longo dentro de um QR Code (para o app do morador, quando existir). **Nenhum dos dois é persistido em claro** — só o HMAC-SHA256; `pickupCodeLast4` fica visível apenas para a portaria conferir qual credencial está sendo citada. `POST /gatehouse/deliveries/redeem` aceita o código ditado ou o payload do QR escaneado, localiza a entrega pelo hash (busca escopada por RLS, então credencial de outro condomínio simplesmente não é encontrada), valida expiração e marca a credencial como usada.
- **Coluna `pickup_code` em texto puro removida** (migration `20260814100000_drop_plaintext_pickup_code`): ela sobrevivia do desenho anterior e anulava o propósito do HMAC — qualquer leitura do banco revelaria a credencial. Junto saiu o endpoint legado `POST /deliveries/:id/collect`, redundante com `/redeem`. Um teste agora afirma explicitamente que o código em claro não aparece em nenhuma coluna da entrega persistida.
- **WhatsApp deixou de ser stub**: o `WhatsAppAdapter` agora fala com a ponte Go + whatsmeow por HTTP, assinando cada requisição com HMAC sobre `${timestamp}.${nonce}.${body}` (mesmo esquema do webhook de telefonia, já que a ponte não tem sessão de usuário). **Sem `WHATSAPP_SERVICE_URL`/`WHATSAPP_SERVICE_SECRET` configurados ele continua um stub honesto**, relatando "não configurada" em vez de fingir entrega — a regra do projeto contra declarar WhatsApp homologado sem teste real segue valendo. O código de retirada é despachado no mesmo outbox dos comunicados, e uma falha de envio nunca derruba o registro da entrega (a encomenda já está fisicamente na portaria).
- **White-label ampliado**: `visualConfig` (JSON validado por Zod) com cores de superfície, tipografia, raio de borda e tema padrão, mesclado token a token na hierarquia igual aos demais campos. Cada valor é revalidado na leitura e de novo no cliente antes de virar CSS custom property — um campo livre aqui seria injeção de CSS, então fontes são lista fechada e cores são hex de 6 dígitos. Tela `/personalizacao` permite editar marca, logo, favicon e todo o tema, no escopo do próprio nível do ator.
- **Frontend**: paleta e tokens alinhados ao PortariaFlow (hex, não oklch, porque o white-label sobrescreve os mesmos tokens em runtime); `BrandingProvider` aplica o tema e limpa os overrides ao trocar de tenant; `PhotoCapture` (câmera ao vivo com troca frontal/traseira e importação do computador) e `QrScanner` (jsqr, decodificação **local** — a imagem nunca sai do dispositivo, só o conteúdo do QR vai ao backend).
- **Bug corrigido**: o picker de unidades pedia `pageSize=200`, acima do teto de 100 da API, e todo select de unidade vinha vazio com 400. Pego clicando na tela, não no código.
- **Bug corrigido**: o `<title>` voltava para "Portalia" a cada navegação porque o metadata do Next reescreve o título depois do efeito de branding; passou a ser reaplicado no `pathname`.
- Verificado ponta a ponta no navegador com um `CONDO_OPERATOR` real: registro de entrega → credencial (código + QR renderizado + validade) → retirada pelo código → some da fila de pendentes; e via API: retirada por QR, rejeição de credencial desconhecida, rejeição de imagem falsificada, e merge do white-label. Suíte completa do zero: **82 unitários + 87 e2e, todos verdes**.

## Rodada de hardening de segurança

Auditoria adversarial em duas levas (workflow multi-agente: dimensão audita, achado é verificado por um segundo agente tentando refutá-lo antes de contar como confirmado). A primeira leva (auth-sessão, injeção/input, DoS/rate-limit, segredos/config, frontend) bateu o limite de cota da sessão no meio da fase de verificação — só 4 achados chegaram a ser genuinamente confirmados; a dimensão `authz-tenant` (isolamento multi-tenant/IDOR) não rodou. Uma segunda leva, menor, cobre especificamente essa lacuna mais uma revisão pontual de 3 achados que ficaram ambíguos na primeira.

**Confirmados pela auditoria e corrigidos:**
- **Corrida entre logout e refresh ressuscitava sessão encerrada** (severidade alta): `refresh()` não tinha como saber que um `logout()` concorrente já havia encerrado a sessão — se a resposta do refresh chegasse depois, ela reescrevia o estado para `authenticated` com um token novo, e o app redirecionava sozinho de volta para dentro, mesmo o operador já tendo saído fisicamente do balcão. Corrigido com um contador de época (`epoch`) no `session-store.ts`, incrementado em todo `login()`/`logout()` e checado antes do `set()` de sucesso do `refresh()` — resultado obsoleto é descartado. No backend, `POST /auth/logout` passou a revogar **todos** os refresh tokens ativos do usuário (por `userId`), não só o token do cookie apresentado, fechando o caso em que o refresh concorrente já tinha rotacionado o token antes do logout chegar.
- **`mustChangePassword` não sobrevivia a um refresh** (severidade média): um F5 na tela de troca de senha obrigatória restaurava a sessão via `/auth/refresh`, que não devolvia esse campo — o gate do cliente reabria o app inteiro com a senha temporária (conhecida pelo admin, entregue por canal inseguro) ainda válida indefinidamente, e o controle nunca foi server-side (a mesma chamada de API funcionava com o token de login). Corrigido em duas pontas: o campo virou uma claim assinada no JWT (`mustChangePassword`), e um novo `MustChangePasswordGuard` (guard global, depois do `JwtAuthGuard`) bloqueia toda rota exceto `/auth/change-password` e `/auth/logout` enquanto a claim for `true` — fechando o gate no servidor, não só no cliente.
  - **Bug novo, descoberto ao verificar essa correção no navegador, não pela auditoria**: como o `mustChangePassword` virou claim do JWT, o access token emitido no LOGIN continua com `mustChangePassword:true` gravado nele mesmo depois de uma troca de senha bem-sucedida (JWT é imutável) — toda chamada seguinte com esse token (inclusive o `GET /platform/white-label` que o `BrandingProvider` dispara globalmente) passou a ser bloqueada pelo guard novo, e como o React Query não repete erro 403 automaticamente, o branding ficava preso em erro até um reload manual. Corrigido fazendo `POST /auth/change-password` emitir uma sessão nova (access + refresh token, como login/refresh) em vez de `204 void`; o frontend (`applyPasswordChange`) troca o token em memória imediatamente, sem precisar de reload. `GET /platform/white-label` também ganhou `@AllowPasswordChangePending()` — branding não é dado sensível e precisa renderizar mesmo na tela de troca de senha.
- **Cache do TanStack Query não era limpo no login/logout** (severidade média): branding e lista de usuários (com e-mail/papel) de um ator ficavam servíveis do cache para o próximo ator autenticado na mesma aba, num terminal compartilhado de portaria/administração. Corrigido com `queryClient.clear()` no `onSubmit` do login e no clique de logout do `AppShell`, antes de qualquer nova query rodar.
- **Open redirect no parâmetro `next` do login** (severidade baixa — a escalada alegada para XSS via `javascript:` foi refutada, o Next 16 já bloqueia esse esquema em duas camadas): `next` ia direto para `router.replace`/`router.push` sem validar que era um caminho interno. Corrigido com `safeNextPath()` (só aceita `/algo`, rejeita `//host` e `/\host`), usado nos dois pontos de navegação.

**Corridos/corrigidos diretamente nesta sessão, sem esperar verificação de agente** (achados óbvios de ler o código, ou identificados por mim ao revisar os arquivos tocados pela auditoria):
- **Contador de tentativas falhas de login não era atômico**: era um read-then-write (`findUnique` → `+1` em JS → `update`) — tentativas de login concorrentes para a mesma conta liam o mesmo valor de partida e cada uma escrevia o mesmo "+1", perdendo tentativas (`lost update` clássico). Um ataque de força bruta com paralelismo esvaziava na prática o bloqueio progressivo que existe justamente para conter esse cenário. Corrigido com `SELECT ... FOR UPDATE` dentro de uma transação em `LoginUseCase.registerFailure`, serializando o incremento por linha. Provado com um teste de concorrência real (`login-throttle-concurrency.e2e-spec.ts`): 8 tentativas de login disparadas em paralelo (`Promise.allSettled`) resultam em `failedLoginAttempts === 8` no banco, não menos.
- **JWT verificado sem fixar algoritmo/emissor/audiência**: `verifyAccessToken` não passava `algorithms`, deixando `jsonwebtoken` decidir com base no `alg` do header do próprio token (a abertura clássica de "algorithm confusion", ainda que sem chave assimétrica no sistema hoje para explorar de fato). Corrigido fixando `algorithms: ['HS256']`, `issuer`, `audience` na verificação, e os mesmos `issuer`/`audience` na assinatura.
- **`JWT_ACCESS_SECRET` reutilizado como chave HMAC da credencial de retirada**: um vazamento do segredo de uma credencial de curto prazo (código de retirada) não deveria comprometer a capacidade de forjar tokens de sessão completos. Nova env var dedicada `PICKUP_CREDENTIAL_SECRET`.
- **Upload de fotos sem limite no multer**: `FileInterceptor('file')` sem `limits` bufferiza o corpo inteiro em memória antes de qualquer checagem — o `MAX_UPLOAD_MB` já existente em `OperationalPhotosService` rejeitava tarde demais (depois do dano de memória já feito). Corrigido com `limits.fileSize` no próprio interceptor (teto de 50MB, o mesmo teto que o schema de `MAX_UPLOAD_MB` já impõe), e o filtro global de exceções passou a traduzir `MulterError` para `413`/`400` em vez de vazar como `500` não tratado (e logado como se fosse bug do servidor).
- **Corpo de requisição sem limite explícito**: dependia do default implícito do `body-parser`. `main.ts` agora desliga o parser automático do Nest e configura `useBodyParser('json'|'urlencoded', {limit:'1mb'})` explicitamente (confirmado que o `rawBody` usado pela verificação HMAC do webhook de telefonia continua intacto com essa mudança — suíte de telefonia revalidada).
- **Rate limit por IP sem `trust proxy`**: atrás de um proxy reverso real, todo tráfego apareceria com o IP do proxy para o `ThrottlerGuard`, ou (pior) um cliente poderia forjar `X-Forwarded-For` se `trust proxy` fosse ligado sem critério. Nova env var `TRUST_PROXY_HOPS` (default `0` = desligado/seguro), setando `app.set('trust proxy', hops)` só quando > 0 e configurada para o número real de proxies confiáveis do deploy.
- **Senha sem limite máximo**: bcrypt trunca silenciosamente em 72 bytes — duas senhas diferentes com o mesmo prefixo de 72 bytes hasheiam igual, e sem teto o campo também aceita payloads gigantes que ainda assim pagam o custo computacional do bcrypt. `newPassword`/`password`/`currentPassword` ganharam `.max()` nos schemas Zod.
- **`/health/ready` vazava detalhe interno de conexão do Postgres**: rota pública (necessária para health check de load balancer) devolvia a mensagem de erro crua do driver (host/porta) quando o banco caía. Corrigido para logar o detalhe completo no servidor e devolver só `{status:'error', database:'down'}` ao chamador.
- **Correlation id aceito do cliente sem validação**: `X-Correlation-Id` virava `req.id`, ecoado em toda linha de log e no header de resposta, sem checagem de formato/tamanho — vetor de log injection e string sem teto em cada linha de log. Corrigido com uma allowlist de formato (`[a-zA-Z0-9_-]{1,100}`); valor fora do padrão é descartado e um UUID novo é gerado.
- **`.gitignore` do backend cobria só o literal `.env`**: variantes comuns (`.env.local`, `.env.production` etc.) não estavam cobertas. Corrigido para `.env` + `.env.*` com exceção explícita de `.env.example`.
- **`storageKey` de gravação de telefonia aceito como string livre**: campo é só metadado hoje (V01 não integra object storage real — nada lê/escreve arquivo a partir dele), mas já está no formato de uma chave de object store; sem validação agora, uma futura integração real herdaria um campo shaped-like-a-path nunca sanitizado. Corrigido com uma allowlist de caracteres e rejeição de `..`, preventivo.
- **Nome de arquivo do multipart persistido sem sanitização**: nunca vira caminho de arquivo (risco de path traversal já não existia), mas caracteres de controle e tamanho ilimitado não pertencem a um campo que pode ser exibido/logado depois. Truncado em 255 chars, caracteres de controle removidos.
- **Paginação sem teto no parâmetro `page`**: `pageSize` já tinha teto de 100, mas `page` não — um valor absurdo vira um `OFFSET` do Postgres caro de processar mesmo quando o resultado é vazio. Teto de 100.000.

**Segunda leva da auditoria** (dimensão `authz-tenant` + revisão pontual de 3 achados ambíguos): bateu o limite de cota da sessão **duas vezes seguidas** antes de conseguir rodar a dimensão `authz-tenant` — ela continua sem cobertura de auditoria adversarial. O agente de "revisão pontual", que rodou por completo antes de a cota estourar de novo, entregou um achado crítico:

- **Oráculo de timing no login estava ATIVO por um bug de formato — a mitigação nunca funcionou** (severidade alta, achado da auditoria confirmado pessoalmente antes de corrigir: contei os caracteres da constante e li o código-fonte do `bcryptjs` instalado): o hash dummy usado para dar forma constante à resposta de login (`'$2a$12$invalidinvalid...'`) tinha **59 caracteres, não 60**. `bcryptjs.compare()` sai fora com `false` em menos de 1ms para qualquer hash cujo tamanho não seja exatamente 60 — nunca chegava a pagar o custo real do bcrypt (~250ms, medido empiricamente com a mesma lib e o mesmo custo 12 usado por `PasswordHasherService`). Resultado: login com email inexistente respondia em poucos ms; login com email existente e senha errada respondia ~250ms depois — um oráculo grosseiro, distinguível numa única requisição de cada tipo, sem precisar de amostragem estatística. Corrigido gerando um hash dummy válido de 60 caracteres (`DUMMY_PASSWORD_HASH`, exportado e travado por teste dedicado que mede o tempo de comparação contra ele e confirma que fica na mesma ordem de grandeza de um hash real, não a de um no-op).
- **Trust proxy confirmado efetivo**: o agente leu o código-fonte instalado do Express e do `@nestjs/throttler` e confirmou que `req.ip` (a chave usada pelo `ThrottlerGuard`) respeita exatamente a configuração `'trust proxy'` que `TRUST_PROXY_HOPS` alimenta — a correção da primeira leva resolve o problema quando configurada com o número real de proxies do deploy. O armazenamento em memória do `ThrottlerModule` (não Redis) é um risco real só numa topologia futura com múltiplas instâncias atrás de load balancer — não há evidência de deploy assim hoje (processo único); registrado como débito técnico para quando a V01 escalar horizontalmente, não corrigido agora.
- **Injeção de operador de filtro do Prisma via query params**: a hipótese mais severa (um objeto de filtro genérico repassado inteiro a um `where`) não existe em lugar nenhum do código — confirmado por busca exaustiva. Mas havia um vetor real e mais estreito: todo `@Query('xId') xId: string` que identifica escopo (condominiumId, unitId, resaleId, clientId — 26 ocorrências em 20 controllers) e dois filtros de texto em audit-logs eram só anotação TypeScript, sem validação em runtime; o parser de query padrão do Express (`qs`) interpreta notação de colchetes (`?condominiumId[not]=x`) como objeto aninhado, que o Prisma tipado aceita como operador de `StringFilter`. RLS já contém o pior caso (um CONDO_MANAGER/OPERATOR de escopo fixo não ganha nada; o pior cenário é um CLIENT_ADMIN/RESALE_ADMIN conseguir listar de uma vez dados que já estava autorizado a ver espalhados, não vazamento cross-tenant), mas corrigido como defesa em profundidade: todo esses parâmetros agora passam por `ZodValidationPipe(scopeIdSchema)` (`z.string().uuid()`) ou `optionalTextFilterSchema`. Confirmado empiricamente, não só por leitura de código: um teste novo manda `?condominiumId[not]=<uuid>`, confere no log que o Express realmente entrega `{condominiumId: {not: '<uuid>'}}` em `req.query`, e que a rota agora responde 400 em vez de aceitar.

Suíte completa (unitários + e2e) revalidada do zero a cada lote de mudanças ao longo de toda a rodada — estado final: **90 unitários + 91 e2e, todos verdes**, lint limpo.

**Dimensão `authz-tenant` (isolamento multi-tenant/IDOR)**: bateu o limite de cota da sessão duas vezes seguidas ao tentar rodar como auditoria multi-agente (audita → verifica adversarialmente). Uma terceira tentativa, com um único agente instruído a auditar e tentar refutar seus próprios achados antes de reportar, completou em ~4 minutos/54 chamadas de ferramenta e devolveu zero achados. Como um resultado vazio de agente não é evidência suficiente por si (poderia ser um agente que não investigou fundo, não necessariamente "nada para achar"), complementei com uma varredura própria, sistemática e não amostral: busquei toda chamada direta ao Prisma (`this.prisma.<model>.<método>`) fora de `withTenantContext` nos 20 services do backend — a assinatura exata de uma leitura/escrita que escapou do escopo de RLS. Toda ocorrência encontrada se justifica por um de quatro motivos legítimos, sem exceção: roda antes de qualquer tenant ser conhecido (login, bootstrap do primeiro super admin); o ator é `SUPER_ADMIN` (`resolveTenantScope` retorna escopo vazio para ele — RLS não mudaria nada mesmo se estivesse presente, confirmado que `PLATFORM_MANAGE`, a permissão que gate `PlansService`, existe *apenas* no papel `SUPER_ADMIN` na tabela `ROLE_PERMISSIONS`); o filtro já usa `actor.resaleId`/`actor.id` do JWT verificado diretamente, nunca um id de payload (`FeatureFlagsService` listando clients/condominiums do próprio `actor.resaleId`); ou a tabela é deliberadamente sem RLS por decisão documentada (idempotency_keys, webhook_nonces, feature_flags, white_label_configs), com todo caminho de escrita que aceita um id de escopo fora do nível do próprio ator revalidando via `resolveWritableScopeId` (RLS-scoped lookup) antes de aceitar — nunca confiando no payload. Também reconfirmei manualmente, lendo o código, os três fluxos mais sensíveis desta sessão (redenção de credencial de retirada por hash, leitura de conteúdo de foto operacional por id, escrita de white-label) — todos escopados corretamente. Isso não substitui uma auditoria adversarial ativa (não houve tentativas reais de exploração automatizadas com múltiplos atores, como as que confirmaram os 4 achados anteriores), mas é uma cobertura de código sistemática e completa da dimensão, não uma amostragem — dou por encerrada esta rodada de hardening com essa dimensão "verificada por revisão, não por ataque", registrado honestamente como a diferença que é.

Achados levantados pela primeira leva mas nunca verificados por falta de cota (rate limit em memória sem armazenamento compartilhado — já avaliado acima como não-crítico hoje —, access token sem revogação antes do TTL expirar, refresh token sem tempo de vida absoluto, transações sem timeout configurado, fan-out de comunicado síncrono) são limitações arquiteturais conhecidas, não corrigidas nesta rodada — a maioria exige uma decisão de trade-off (ex.: revogar access token exigiria checar uma blocklist a cada requisição, custo que a V01 não paga hoje) mais adequada para discutir com o usuário do que para decidir unilateralmente.

## App mobile — morador e porteiro (iOS + Android)

Rodada motivada por um requisito de produto: substituir o interfone físico de
parede (caro de manter, fiação frágil, difícil de cadastrar morador novo) por
um app no estilo Mobility Pro (Intelbras) / PortSIP, com chamada tocando
mesmo com o app fechado. Layout desenhado e aprovado com o usuário antes de
qualquer código (5 abas: Comunidade, Interfone, Início centralizado,
Entregas, Perfil).

**Achado que redefiniu o escopo**: o backend só sabia autenticar *equipe*.
`Resident` era um registro operacional puro — sem senha, sem login, sem
relação com `User`. Nenhum endpoint existente podia ser chamado por um
morador. Antes de qualquer tela, o backend precisou de uma segunda porta de
autenticação.

- **`resident-auth`, deliberadamente paralelo a `auth`** (não estende
  `UserRole`/`ROLE_PERMISSIONS`/`ROLE_DEPTH`): esses três `Record` exaustivos
  assumem hierarquia de equipe com 4 profundidades fixas de tenant, e um
  morador não é "staff mais raso" — ele só enxerga a própria unidade e nunca
  gerencia nada. Forçá-lo naquele modelo distorceria a semântica de
  provisionamento (`canProvisionRole`). Migration
  `20260814120000_resident_auth` adiciona os campos de auth em `Resident`
  (com `email` virando `@unique`, já que Postgres permite múltiplos NULL) e
  cria `ResidentRefreshToken` com a mesma RLS de três níveis do resto.
- **Mobile-first onde o fluxo de equipe é browser-first**: o refresh do
  morador aceita o token no **corpo** da requisição (o app guarda em
  Keychain/Keystore e reapresenta explicitamente), sem cookie e sem CSRF —
  double-submit cookie não faz sentido para um cliente nativo. O fluxo de
  equipe continua intocado (cookie httpOnly + CSRF), porque o painel web
  depende dele.
- **Isolamento de audience**: token de morador usa
  `audience: 'portalia-resident-app'`, o de equipe `'portalia-app'`. Ambos
  assinados com a mesma `JWT_ACCESS_SECRET`, mas nenhum passa no guard do
  outro — coberto por teste que tenta os dois cruzamentos.
- **`resident/*`**: `me`, `dashboard` (contagens da própria unidade — o
  `ReportsService.overview` existente só agrega por condomínio inteiro),
  `announcements`, `deliveries` e reemissão de credencial de retirada, mais
  `telephony/credentials`. **A RLS não tem nível de unidade** (só
  resale/client/condominium), então o filtro por `unitId` é responsabilidade
  do código — provado por teste que confirma que um morador da unidade A não
  vê nem consegue reemitir credencial da unidade B, no mesmo condomínio.
- **Bug real encontrado ao construir**: `IdempotencyInterceptor` lê
  `request.actor` (ator de equipe), que numa rota de morador é sempre
  `undefined` — a reemissão de credencial teria estourado em toda chamada.
  Corrigido com `ResidentIdempotencyInterceptor`/`@ResidentIdempotent`, que
  leem `request.residentActor`.
- **`decryptSipPassword` deixou de ser código morto**: até aqui só era
  exercitada em teste. `GET /resident/telephony/credentials` é o primeiro
  chamador real em produção. Sem `SIP_DOMAIN` configurada, responde
  `configured:false` mesmo com o ramal existindo — o app mostra "SIP
  aguardando configuração" em vez de fingir que registrou.
- **Provisionamento**: `createResident` passou a gerar senha temporária e
  devolvê-la em claro **uma única vez** (mesmo padrão da senha SIP e do
  código de retirada), com dialog de revelação na aba Moradores do painel web.

**Flakiness de teste diagnosticada e corrigida** (não era do código novo):
`auth-flow.e2e-spec.ts` falhava de forma aparentemente aleatória em rodadas
completas. Causa raiz: `BootstrapSuperAdminUseCase` procura por *qualquer*
`SUPER_ADMIN`, então `created: true` só é verdade num banco sem nenhum — mas
três outros arquivos de teste criam super admins próprios, e um
`npm run bootstrap:super-admin` rodado à mão no banco de dev deixa um
permanente. O teste presumia a pré-condição em vez de garanti-la. Junto,
um segundo bug latente no mesmo arquivo: `admins[0].mustChangePassword`
checava um super admin arbitrário (sem `orderBy`), não o do bootstrap.
Corrigidos; **três rodadas completas consecutivas verdes** depois da
correção. Débito registrado: a suíte e2e roda contra o mesmo banco de dev,
e agora limpa super admins — isolar num banco `portalia_test` é o próximo
passo natural.

**Apps** (`mobile/ios`, `mobile/android`): um app por plataforma, mostrando a
UI de morador ou de porteiro conforme o papel da conta (nunca os dois no
mesmo aparelho). Swift/SwiftUI + XcodeGen, Kotlin/Compose + Gradle, cada um
com um módulo core compartilhado (rede, sessões, modelos, interface de SIP).
CallKit/PushKit (iOS) e Telecom self-managed/FCM (Android) são código real —
frameworks de plataforma, sem dependência externa — mas inertes até haver
Asterisk, conta Apple Developer e projeto Firebase reais. `docs/mobile/SIP_PUSH.md`
lista os 8 passos que faltam, incluindo um que não existe no backend hoje:
nenhum endpoint registra push token de dispositivo contra o morador/unidade.

**Limitação honesta desta entrega**: o código mobile **nunca foi compilado** —
o ambiente de desenvolvimento é Windows, sem Xcode (impossível: Mac-only) e
sem Android SDK/Gradle. Bugs reais foram encontrados relendo o código contra
os contratos do backend (shape errado da resposta de change-password nos dois
apps, `ContentUnavailableView` exigindo iOS 17 contra um alvo iOS 16,
`gradle-wrapper.properties` ausente), mas nada substitui a primeira build de
verdade. Testes de contrato de decodificação (`DecodingContractTests.swift`)
foram escritos contra os JSONs reais dos mappers do backend justamente
porque essa é a classe de bug que mais apareceu aqui.

Estado final do backend: **87 unitários + 104 e2e, todos verdes**, lint e
type-check limpos nos dois lados, build de produção do frontend passando.
